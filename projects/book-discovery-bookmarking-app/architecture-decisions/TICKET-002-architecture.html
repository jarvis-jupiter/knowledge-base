Key topology note: The Remix app is a Node.js server. Loaders and actions run on the Remix server and call the Express API via HTTP using a stored JWT bearer token (retrieved from the Remix session). The browser never makes direct API calls — all data flows through Remix loaders/actions.

Hexagonal topology note: Express route handlers are inbound adapters — they receive HTTP, call use cases, and return HTTP. Use cases live in the application layer and know nothing about HTTP or Prisma. Prisma implementations are outbound adapters — they implement port interfaces injected into use cases.

4. Data Model

4.1 users Table

CREATE TABLE users (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email        TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

Prisma Schema:

model User {
  id           String     @id @default(uuid())
  email        String     @unique
  passwordHash String
  createdAt    DateTime   @default(now())
  bookmarks    Bookmark[]
}

4.2 bookmarks Table

Bookmark storage stores the Google Books volume ID plus the essential display metadata (title, authors, thumbnail). This allows the bookmark list to render without a live API call on every page load — a key spec decision from TICKET-002 Rationale.

CREATE TABLE bookmarks (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id          UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  google_volume_id TEXT NOT NULL,
  title            TEXT NOT NULL,
  authors          JSONB NOT NULL DEFAULT '[]',   -- string[]
  thumbnail_url    TEXT,
  description      TEXT,
  bookmarked_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (user_id, google_volume_id)              -- idempotency constraint
);

Prisma Schema:

model Bookmark {
  id             String   @id @default(uuid())
  userId         String
  googleVolumeId String
  title          String
  authors        Json     @default("[]")
  thumbnailUrl   String?
  description    String?
  bookmarkedAt   DateTime @default(now())
  user           User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, googleVolumeId])
}

Key design decisions:

  • UNIQUE(user_id, google_volume_id) enforces idempotency at the DB level (AC 4: no duplicate bookmarks).
  • authors stored as JSONB array — avoids a junction table for MVP; sufficient for display.
  • thumbnail_url and description nullable — Google Books may not provide them (AC 7: graceful omission).

5. API Contract

Base URL: /api Content-Type: application/json Auth: Authorization: Bearer <jwt> header. Remix loaders/actions attach this header using the JWT stored in the Remix session cookie (server-side only — never exposed to the browser).

5.1 Auth Endpoints

POST /api/auth/register

Request:

{ "email": "user@example.com", "password": "mypassword" }

Responses:

  • 201 Created — returns { "token": "<jwt>", "user": { "id": "...", "email": "..." } }
  • 400 Bad Request — { "error": "Password must be at least 8 characters" }
  • 409 Conflict — { "error": "Email already in use" }

Remix integration: The /register route action calls this endpoint, extracts the token from the response, stores it in the Remix session via createCookieSessionStorage, then redirects to /search.

Maps to AC 1 (Registration)

POST /api/auth/login

Request:

{ "email": "user@example.com", "password": "mypassword" }

Responses:

  • 200 OK — returns { "token": "<jwt>", "user": { "id": "...", "email": "..." } }
  • 401 Unauthorized — { "error": "Invalid email or password" } (intentionally ambiguous — AC 2)

Remix integration: The /login route action calls this endpoint, stores the token in Remix session, redirects to /search.

Maps to AC 2 (Login)

POST /api/auth/logout

No request body. Backend invalidation is stateless (JWT expiry handles it).

Responses:

  • 200 OK — { "message": "Logged out" }

Remix integration: The /logout route action destroys the Remix session (removes the stored JWT), then redirects to /login. No backend call is strictly required; session destruction is sufficient.

Maps to AC 8 (Logout)

5.2 Book Endpoints (Google Books Proxy)

The Express backend proxies all Google Books calls to keep the API key server-side and centralise error handling. Remix loaders call these endpoints server-to-server.

GET /api/books/search?q=<query>

Proxies: https://www.googleapis.com/books/v1/volumes?q=<query>&maxResults=20&key=<API_KEY>

Auth required: Yes (Bearer token)

Response 200 OK:

{
  "results": [
    {
      "volumeId": "abc123",
      "title": "Clean Code",
      "authors": ["Robert C. Martin"],
      "description": "A handbook of agile software craftsmanship...",
      "thumbnailUrl": "https://books.google.com/books/content?id=abc123&...",
      "publisher": "Prentice Hall",
      "publishedDate": "2008-08-01",
      "pageCount": 431,
      "categories": ["Computers"]
    }
  ],
  "totalItems": 42
}

Error responses:

  • 400 — missing q parameter
  • 502 Bad Gateway — Google Books API unreachable → { "error": "Book search temporarily unavailable" }
  • 401 Unauthorized — invalid or missing token

Remix integration: The /search route loader reads q from request.url, attaches the Bearer token from the session, calls this endpoint, and returns the normalised results to the component via useLoaderData().

Maps to AC 3 (Book Search)

GET /api/books/:volumeId

Proxies: https://www.googleapis.com/books/v1/volumes/:volumeId?key=<API_KEY>

Auth required: Yes

Response 200 OK: Same shape as a single result in search, with all detail fields (full description, no truncation).

Error responses:

  • 404 Not Found — volume not found in Google Books
  • 502 Bad Gateway — Google Books API error

Remix integration: The /books/:volumeId route loader calls this endpoint and returns data to the component.

Maps to AC 7 (Book Detail Page)

6. Authentication Design

6.1 Flow

Register / Login (browser submits Remix <Form>)
      │
      ▼
Remix action runs server-side
      │
      ▼
Remix action calls POST /api/auth/register or /login (Express)
      │
      ▼
Express inbound adapter → calls registerUser / loginUser use case
      │
      ▼
Use case calls UserRepository (outbound port) → Prisma adapter → DB
      │
      ▼
Use case returns domain result → adapter maps to HTTP response { token, user }
      │
      ▼
Remix action stores token in Remix session:
  session.set("token", token)
  session.set("userId", user.id)
  Set-Cookie: __session=<signed-session>; HttpOnly; SameSite=Lax; Secure; Path=/
      │
      ▼
Browser stores signed session cookie automatically (no JS access — XSS safe)
      │
      ▼
Subsequent Remix loaders/actions:
  1. Read session from cookie: await getSession(request.headers.get("Cookie"))
  2. Extract token: session.get("token")
  3. Attach to backend call: Authorization: Bearer <token>
  4. If no token → redirect to /login

6.2 Route Protection

Backend: verifyToken middleware applied to all /api/books/* and /api/bookmarks/* routes. Validates Bearer token from Authorization header.

Frontend (Remix): Each protected loader checks the session for a valid token via a requireUserSession(request) helper. If absent, it throws redirect("/login"). This provides both UX-level and server-level protection in one place — no separate route guard component needed.

AC 9 (Access control): Covered by backend middleware (API-level) and Remix loader guards (render-level). Unauthenticated requests are redirected before any data is fetched.

7. Google Books API Integration Pattern

Browser navigates to /search?q=clean+code
      │
      ▼
Remix loader (search.tsx) — runs server-side:
  1. requireUserSession(request) → get token
  2. Extract q from new URL(request.url).searchParams
  3. Call GET /api/books/search?q=<query> with Bearer token
      │
      ▼
Express inbound adapter (interfaces/http/books.ts):
  1. Validates Bearer token (verifyToken middleware)
  2. Calls searchBooks use case with { bookSearchService } injected
      │
      ▼
searchBooks use case (application/use-cases/searchBooks.ts):
  1. Calls bookSearchService.search(query) — outbound port
  2. Returns BookResult[] domain objects (never raw Google API response)
      │
      ▼
GoogleBooksAdapter (infrastructure/google-books/):
  1. encodeURIComponent(query)
  2. GET https://www.googleapis.com/books/v1/volumes?q=<encoded>&maxResults=20&key=${KEY}
  3. On success: normalize → BookResult[]
  4. On error: throw GoogleBooksApiError → adapter catches → 502
  5. On empty: return { results: [], totalItems: 0 }
      │
      ▼
Remix loader returns normalised data → component renders via useLoaderData()
No client-side fetch; no loading spinners from data layer

Transformation layer (GoogleBooksAdapter.normalize):

  • Maps volumeInfo.imageLinks.thumbnail → thumbnailUrl (null if absent)
  • Maps volumeInfo.authors → authors (empty array if absent)
  • Truncates description to 200 chars for search results (AC 3b) — pure function in domain/
  • Full description returned on detail endpoint
  • Any missing field → null / omitted gracefully (AC 7b)

API Key: Stored in GOOGLE_BOOKS_API_KEY env variable on the Express server. Never present in the Remix app environment. Backend logs a warning on startup if key is absent.

8. Backend Architecture — Hexagonal (Ports & Adapters)

The backend follows the Hexagonal Architecture (also known as Ports & Adapters) pattern. The core rule is the Dependency Rule: source code dependencies only point inward — outer layers depend on inner layers, never the reverse.

8.1 Layer Diagram

┌─────────────────────────────────────────────────────────────────┐
│  INTERFACES (Inbound Adapters)                                  │
│  interfaces/http/  — Express route handlers                     │
│  They call use cases via inbound ports.                         │
│  They know about HTTP. The use cases do not.                    │
│                                                                 │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  APPLICATION (Use Cases + Ports)                          │  │
│  │  application/use-cases/  — one file per operation         │  │
│  │  application/ports/      — TypeScript interfaces only     │  │
│  │  Use cases know about domain + ports. Not HTTP, not ORM.  │  │
│  │                                                           │  │
│  │  ┌─────────────────────────────────────────────────────┐  │  │

8.2 Domain Layer (domain/)

The innermost layer. Contains:

  • Entities: User, Bookmark, Book — plain TypeScript objects/types, no class inheritance from frameworks
  • Value Objects: Email, VolumeId, PasswordHash — types that enforce invariants
  • Domain Errors: DuplicateEmailError, InvalidCredentialsError, BookNotFoundError, BookmarkNotFoundError, DuplicateBookmarkError

// domain/entities/Bookmark.ts

Rule: No import from Express, Prisma, jsonwebtoken, or any infrastructure package is permitted in domain/.

8.3 Application Layer — Outbound Ports (application/ports/)

Port interfaces define the boundary between the application layer and the outside world. Use cases depend on these interfaces — never on concrete implementations.

  findById(id: string): Promise<User | null>;
  create(email: string, passwordHash: string): Promise<User>;

// application/ports/BookmarkRepository.ts
import type { Bookmark } from "../../domain/entities/Bookmark";

export interface BookmarkRepository {
  findByUserId(userId: string): Promise<Bookmark[]>;

Rule: These files contain only TypeScript interface declarations. No import from Prisma, Express, or any adapter is permitted here.

8.4 Application Layer — Use Cases (application/use-cases/)

Each business operation is a dedicated module. Use cases follow a curried/dependency-injected signature:

(deps: { repo, service, ... }) => (input) => Promise<output>

This is consistent with the FP constraints in Section 10: the outer function binds dependencies (impure at composition root), the inner function is a pure-as-possible operation that produces a domain result.

All seven use cases:

registerUser

// application/use-cases/registerUser.ts
import type { UserRepository } from "../ports/UserRepository";
import type { User } from "../../domain/entities/User";
import { DuplicateEmailError } from "../../domain/errors";
import { hashPassword } from "../../domain/services/passwordService";

type Deps = { userRepo: UserRepository };
type Input = { email: string; password: string };
type Output = { user: User; token: string };

export const registerUser =
  (deps: Deps) =>
  async (input: Input): Promise<Output> => {
    const existing = await deps.userRepo.findByEmail(input.email);
    if (existing) throw new DuplicateEmailError();
    const passwordHash = await hashPassword(input.password);
    const user = await deps.userRepo.create(input.email, passwordHash);
    const token = issueToken(user.id);   // pure JWT signing fn from domain
    return { user, token };
  };

loginUser

// application/use-cases/loginUser.ts
type Deps = { userRepo: UserRepository };
type Input = { email: string; password: string };
type Output = { user: User; token: string };

export const loginUser =
  (deps: Deps) =>
  async (input: Input): Promise<Output> => {
    const user = await deps.userRepo.findByEmail(input.email);
    if (!user) throw new InvalidCredentialsError();
    const valid = await verifyPassword(input.password, user.passwordHash);
    if (!valid) throw new InvalidCredentialsError();
    const token = issueToken(user.id);
    return { user, token };
  };

8.5 Infrastructure Layer — Outbound Adapters

PrismaUserRepository (infrastructure/db/PrismaUserRepository.ts)

Implements UserRepository using Prisma. The Prisma client is constructed here, never in the application layer.

import { PrismaClient } from "@prisma/client";
import type { UserRepository } from "../../application/ports/UserRepository";
import type { User } from "../../domain/entities/User";

export class PrismaUserRepository implements UserRepository {
  constructor(private prisma: PrismaClient) {}

  async findByEmail(email: string): Promise<User | null> {
    return this.prisma.user.findUnique({ where: { email } });
  }
  async findById(id: string): Promise<User | null> {
    return this.prisma.user.findUnique({ where: { id } });
  }
  async create(email: string, passwordHash: string): Promise<User> {
    return this.prisma.user.create({ data: { email, passwordHash } });
  }
}

PrismaBookmarkRepository (infrastructure/db/PrismaBookmarkRepository.ts)

Implements BookmarkRepository using Prisma.

export class PrismaBookmarkRepository implements BookmarkRepository {
  constructor(private prisma: PrismaClient) {}
  findByUserId(userId: string) { return this.prisma.bookmark.findMany({ where: { userId } }); }
  findByUserAndVolume(userId: string, googleVolumeId: string) {
    return this.prisma.bookmark.findUnique({ where: { userId_googleVolumeId: { userId, googleVolumeId } } });
  }
  upsert(input: CreateBookmarkInput) {
    return this.prisma.bookmark.upsert({
      where: { userId_googleVolumeId: { userId: input.userId, googleVolumeId: input.googleVolumeId } },
      create: input,
      update: {},
    });
  }
  async deleteByUserAndVolume(userId: string, googleVolumeId: string): Promise<void> {
    await this.prisma.bookmark.delete({ where: { userId_googleVolumeId: { userId, googleVolumeId } } });
  }
}

GoogleBooksAdapter (infrastructure/google-books/GoogleBooksAdapter.ts)

Implements BookSearchService using fetch against the Google Books API.

export class GoogleBooksAdapter implements BookSearchService {
  constructor(private apiKey: string) {}

  async search(query: string) {
    const url = `https://www.googleapis.com/books/v1/volumes?q=${encodeURIComponent(query)}&maxResults=20&key=${this.apiKey}`;
    const res = await fetch(url);
    if (!res.ok) throw new GoogleBooksApiError("Book search temporarily unavailable");
    const data = await res.json();
    return { results: (data.items ?? []).map(normalizeVolume), totalItems: data.totalItems ?? 0 };
  }

  async getDetail(volumeId: string) {
    const res = await fetch(`https://www.googleapis.com/books/v1/volumes/${volumeId}?key=${this.apiKey}`);
    if (res.status === 404) throw new BookNotFoundError(volumeId);
    if (!res.ok) throw new GoogleBooksApiError("Book detail temporarily unavailable");
    return normalizeVolume(await res.json());
  }
}

normalizeVolume is a pure function (see FP constraints) that maps raw Google Books volume JSON to the domain BookResult type.

8.6 Interfaces Layer — Inbound Adapters (interfaces/http/)

Express route handlers are inbound adapters. They:

  1. Parse and validate HTTP input (Zod)
  2. Extract JWT identity (verifyToken middleware)
  3. Call the appropriate use case with injected dependencies
  4. Map domain results (or domain errors) to HTTP responses
// interfaces/http/auth.ts

router.post("/register", async (req, res) => {

10.2 Test-Driven Development (TDD) — First-Class Constraint

TDD is mandatory at all layers. This is not an afterthought — it is the primary development workflow.

The rule:

A failing test must be written before any implementation code. A feature is not considered done until all its tests pass.

This applies to:

  • Unit tests (Vitest): pure functions in domain/, application/use-cases/, and utils/transforms.ts. Use cases are tested with mock/stub implementations of port interfaces — no Prisma, no HTTP required.
  • Integration tests (Vitest + Supertest): Express route handlers (inbound adapters) calling a test database via real Prisma repositories
  • E2E tests (Playwright): full user journey against a running app (see Section 12)

TDD workflow per feature:

  1. Read the AC for the feature from TICKET-002.md
  2. Write a failing test that encodes the AC
  3. Write the minimum implementation to make the test pass
  4. Refactor (clean up, extract helpers) — tests must remain green
  5. Repeat for the next AC

Hexagonal architecture makes unit testing trivial: use cases depend only on port interfaces. Tests inject fake/stub implementations of UserRepository, BookmarkRepository, and BookSearchService — no database, no HTTP, no test doubles of Prisma models needed.

No feature is mergeable with a failing test. CI must run all tests on every PR; the PR gate blocks merge on any failure.

11. Functional Programming Constraints

These constraints apply to both the frontend (Remix routes, components, utils) and the backend (domain, application layer, utils).

Hexagonal Architecture and FP are deeply complementary. The hexagonal layering enforces what FP demands anyway: push all side effects (Prisma, HTTP, JWT signing, hashing) to the outermost adapters; keep the domain and application layers pure. Use cases are pure functions in the FP sense — their inner functions take data in and return data out, with no side effects. Side effects enter only at the infrastructure and interfaces layers (the hexagon's edge), exactly where adapters live. This means every use case, every domain function, and every transformation utility can be tested with pure function calls — no mocks of frameworks, no test databases, no HTTP servers.

11.1 Pure Functions

Every business logic function must be pure: given the same input, it always returns the same output, and it has no side effects.

// ✅ Pure — always same output for same input, no side effects
const truncateDescription = (desc: string, maxLength: number): string =>
  desc.length <= maxLength ? desc : `${desc.slice(0, maxLength)}...`;

// ❌ Impure — reads external state, mutates
const truncateDescription = (desc: string): string => {
  config.lastTruncated = desc; // side effect
  return desc.slice(0, globalMaxLength); // reads external state
};

11.2 Composition Over Inheritance

Build complex logic by composing small, single-purpose functions. Do not use classes with inheritance hierarchies in business logic. (Adapter classes — PrismaUserRepository, GoogleBooksAdapter — are permitted as they implement port interfaces, but they must not contain business logic.)

// ✅ Composed from small pure functions
const normalizeBook = (volume: GoogleBooksVolume): BookResult => ({
  volumeId: extractVolumeId(volume),
  title: extractTitle(volume),
  authors: extractAuthors(volume),
  thumbnailUrl: extractThumbnailUrl(volume),
  description: truncateDescription(extractDescription(volume), 200),
});

11.3 Immutability

Never mutate objects or arrays. Use spread, map, filter, and reduce for all transformations.

// ✅ Immutable
const addBookmark = (bookmarks: Bookmark[], newBookmark: Bookmark): Bookmark[] =>
  [...bookmarks, newBookmark];

const removeBookmark = (bookmarks: Bookmark[], volumeId: string): Bookmark[] =>
  bookmarks.filter(b => b.googleVolumeId !== volumeId);

// ❌ Mutation
bookmarks.push(newBookmark);
bookmarks.splice(index, 1);

11.4 No FP Libraries

Use native TypeScript only. The following libraries are explicitly prohibited:

  • fp-ts
  • ramda
  • lodash/fp
  • sanctuary
  • Any other functional programming utility library

Native Array.prototype methods, Object.assign, spread syntax, and structuredClone are sufficient.

11.5 Side Effects at the Edge

Side effects (database calls, HTTP calls, session reads/writes, logging) must be isolated at the outermost layer and kept out of business logic functions.

Backend (Hexagonal):

  • Prisma calls live exclusively in infrastructure/db/ (outbound adapters) — never in application/ or domain/
  • fetch calls to Google Books live exclusively in infrastructure/google-books/ — never in use cases
  • Use cases receive port interface implementations via dependency injection (function parameter)
  • The composition root (src/index.ts) is the only place that connects concrete adapters to use cases

Frontend:

  • fetch calls belong in Remix loaders and actions only
  • utils/transforms.ts contains only pure transformation functions
  • Components receive data as props or via useLoaderData() — no useEffect data fetching
// ✅ Inbound adapter (side effects: HTTP parsing, use case call, HTTP response)
router.post("/bookmarks", verifyToken, async (req, res) => {
  const parsed = createBookmarkSchema.safeParse(req.body);
  if (!parsed.success) return res.status(400).json({ error: parsed.error.issues[0].message });
  const bookmark = await addBookmark({ bookmarkRepo })(
    { ...parsed.data, userId: req.user.userId }
  );
  res.status(201).json({ bookmark });
});

// ✅ Use case (application layer — no side effects; Prisma hidden behind port)
export const addBookmark =
  (deps: { bookmarkRepo: BookmarkRepository }) =>
  (input: CreateBookmarkInput): Promise<Bookmark> =>
    deps.bookmarkRepo.upsert(input);

// ✅ Outbound adapter (side effects: Prisma upsert)

  return this.prisma.bookmark.upsert({ ... });
}

16. Key Design Decisions Summary

Decision Choice Reason
Frontend framework Remix + TypeScript SSR, file-based routing, loaders/actions eliminate client-side data-fetching layer; reduces bundle size and complexity
Backend architecture Hexagonal (Ports & Adapters) Domain and application layers have zero framework/infrastructure imports; use cases are pure functions; dependencies always point inward; enables unit testing without databases or HTTP servers
Repository pattern UserRepository, BookmarkRepository interfaces in application/ports/ Use cases never import Prisma; concrete implementations swappable; Prisma isolated to infrastructure/db/
Use case pattern One function per operation, curried (deps) => (input) => Promise<output> Consistent with FP constraints; pure inner function; dependencies injected at composition root; trivially testable with stub implementations
Backend framework Express 5 + Node.js Lightweight inbound adapter; suits proxy workloads; does not contaminate use cases
Database PostgreSQL + Prisma Relational integrity; Prisma type safety; Prisma confined to outbound adapter layer
Auth mechanism JWT returned in response body; stored in Remix session cookie (signed, HttpOnly) XSS-safe; session management owned by Remix; no JWT in browser localStorage
Data flow All API calls via Remix loaders/actions (server-to-server) Browser never calls Express directly; no client-side fetch required
Google Books proxy Express backend via GoogleBooksAdapter Keeps API key server-side; isolated behind BookSearchService port
Bookmark metadata storage Store snapshot at bookmark time Bookmark list renders without live API call; tolerant of Google Books changes
Idempotency DB unique constraint + upsert No duplicate bookmarks even under concurrent requests
Description truncation 200 chars in search, full in detail Matches AC 3b / AC 7 spec requirements
Authors storage JSONB array in Postgres Simple for MVP; avoids unnecessary join table
TDD Mandatory at all layers Failing tests written first; hexagonal architecture makes use case unit tests trivial (stub ports)
FP constraints Pure functions, immutability, composition, native TS only Hexagonal layering enforces side-effect isolation; use cases are pure; adapters contain all side effects
E2E framework Playwright (Chromium) Official docs recommend Playwright for modern web; covers all ACs
Docs-first Official docs read before coding Prevents anti-patterns; ensures framework is used as intended
