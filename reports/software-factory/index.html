Foundation

What is a Software Factory?

🏭

The Core Idea

A software factory applies industrial engineering principles — standardisation, automation, assembly-line thinking — to software production. Not a physical place, but an organisational model for repeatable, high-throughput delivery.

🔭

Two Readings

SE lens: systematic reuse, product lines, CI/CD pipelines — the software discipline itself treated as a factory.

Manufacturing lens: physical factories becoming software-driven — production reconfigured at the code layer, not the hardware layer.

📅

Origins

Traced to Hitachi Software Works, Japan, 1960s–70s. Formalised in SE research through the 1990s (Cusumano, Griss). Revived with force in 2020s by AI and cloud-native tooling.

Core Principles
📦

Standardisation

Repeatable processes, consistent component designs, enforced conventions across every product line.

⚙️

Automation

Code generation, CI/CD, test automation — removing manual steps from the path to production.

🧩

Reuse

Modular architecture, shared libraries, and product families built on a common managed base.

📊

Measurement

Quantitative feedback loops — throughput, defect density, cycle time — managed like an engineered system.

The concept resurfaces in every automation wave — each time with broader scope, shorter cycle times, and higher autonomy. The question shifts from whether to automate to at which abstraction level the human operates.

Software Engineering Lens

Building software like an assembly line

📐

Software Product Lines

A family of related applications built from a shared architecture and a managed set of reusable components. Variation points handle per-product customisation. Concentrates quality effort at the core rather than duplicating it per product.

Feature models Variability management
🗣️

Domain-Specific Languages

DSLs let domain experts author high-level intent that generators compile into lower-level artefacts — model-driven engineering (MDE). In 2024–25, Gen AI collapses this further: natural language becomes the DSL, with the LLM as the compiler.

MDE Gen AI as compiler
🔄

CI/CD as the Factory Line

CI/CD pipelines are the modern realisation of the software factory — automated build, test, security scan, and release stages every commit traverses. By 2025, AI is embedded directly into pipeline stages for intelligent triage, auto-fix, and anomaly detection.

DevOps AI-augmented CI

2025 shift: AI coding assistants are entering the factory line itself — generating code, writing tests, reviewing diffs, handling repetitive refactors. A 2025 IEEE survey found 68% of developers using AI assistants cut development time by at least 35%.

Where AI Is Being Applied
📝

Requirements & Spec

LLMs extract structured requirements from natural language briefs, generate user stories, and surface ambiguity — compressing the PM–Dev handoff significantly.

💻

Code Generation & Review

AI coding assistants (Copilot, Cursor, Claude Code) generate boilerplate, suggest refactors, complete functions from docstrings, explain diffs. Junior developers focus earlier on architecture rather than syntax.

🧪

AI generates unit tests, E2E scenarios, fuzz inputs. Mutation testing coverage analysis is automated. Flaky test detection and root-cause suggestion are active research areas in 2025.

🔒

Security & Compliance

AI-assisted SAST/DAST flags vulnerabilities in PRs. LLMs explain CVEs in context, suggest fixes, validate compliance against policy codebases.

🚀

Operations & Observability

AI correlates logs, traces, and metrics to detect anomalies and predict failures — feeding back into the factory's quality loop.

Academic Research

Open questions & the education frontier

Research Themes 2024–2025
🎓

Higher Education Roadmaps

AIP Conference Proceedings (2025): universities building internal software factories to industrialise student project delivery and foster industry links. Agile methods, shared CI/CD platforms, and peer review cycles are the key ingredients.

🔬

Addressing the Software Crisis

Long-standing challenge: high cost, schedule overruns, quality failures. The factory model resurfaces as the structural answer. Current research: which primitives — product lines, platform engineering, AI agents — best reduce entropy at scale.

🤖

IT/OT Convergence Security

As factory floors connect to cloud systems, OT security demands collide with IT development pace. AI agents with exec permissions are a significant attack surface. Least-privilege tooling is the first defence — but the research is young.

Open Research Problems

🤖 Agent accountability

When a multi-agent factory introduces a defect, who is responsible? How do audit trails, human gates, and explainability frameworks distribute accountability across an autonomous pipeline?

📏 Measuring factory quality

Traditional metrics (velocity, defect density) are insufficient for AI-assisted factories. What metrics capture the quality of the factory itself — not just the artefacts it produces?

🔄 Factory composition

Can factories be composed across organisations? Standard interfaces for inter-factory handoffs — specs, test reports, deployment contracts — remain an open problem.

🧠 Cognitive offloading

Anthropic (2025): heavy AI reliance causes measurable skill erosion in junior developers. Pedagogy must balance productivity acceleration with foundational depth.

The Agent Factory

Why agents map perfectly to the factory model

🧠

The Problem

A single general-purpose agent doing everything — planning, coding, testing, deploying — loses specialisation. A human software team works because each role has deep context, dedicated tools, and clear accountability. The same applies to agents.

🏭

The Insight

OpenClaw agents are fully isolated brains — each gets its own workspace, SOUL.md persona, tool policy, and session store. This maps precisely to a professional role definition. Specialisation, isolation, composability.

🔗

The Glue

sessions_send passes structured work between agents. sessions_spawn enables parallelism. A shared /factory/ filesystem acts as the persistent handoff medium — artefacts survive session restarts and context compaction.

Agent Persona

Product Manager — SOUL.md

~/.openclaw/workspace-pm/SOUL.md
# SOUL.md — Product Manager Agent > *"Clarity is the product."* ## Identity You are a senior product manager embedded in a software factory pipeline. Your only output is structured specification — never code, never test scripts.
## Responsibilities Parse raw requirements from Sir into epics, user stories, and task breakdowns Write acceptance criteria in Given/When/Then format for every story Resolve ambiguity by making an explicit decision and documenting the rationale Produce a prioritised backlog in /factory/specs/TICKET-NNN.md Update /factory/status.json stage to "dev" when spec is ready Notify the Dev agent via sessions_send with the ticket ID and spec path
## Output Format — TICKET-NNN.md Epic: one-line business goal User Stories: As a [role], I want [action], so that [outcome] Acceptance Criteria: Given / When / Then, numbered Out of Scope: explicit exclusions to prevent scope creep Dependencies: blockers, external APIs, data requirements
## Constraints No exec tool — you do not run commands No code — if you write code, you have failed your role No ambiguity — every open question must be resolved, not deferred
Design Notes
🔒

No exec — by design

The PM agent cannot run shell commands. This is a tool policy constraint in openclaw.json. Its blast radius is limited to writing spec files. It cannot accidentally modify source code or run deployments.

📋

Structured output as the contract

The TICKET-NNN.md format is the formal interface between PM and Dev. Dev reads the file directly from /factory/specs/ — no context is passed through conversation; the file is the source of truth.

🎯

Resolve, don't defer

A key instruction: if the requirement is ambiguous, the PM makes an explicit documented decision rather than leaving an open question for Dev to resolve. This prevents downstream rework and responsibility gaps.

📣

Notify, then stop

Once the spec is written and status updated, PM sends a sessions_send to Dev and idles. It does not monitor Dev's progress or follow up unless Sir re-engages it.

Agent Persona

Developer — SOUL.md

~/.openclaw/workspace-dev/SOUL.md
# SOUL.md — Developer Agent > *"Ship it clean, or don't ship it."* ## Identity You are a senior software engineer in a software factory pipeline. You implement, test, commit, and open PRs. You respond to QA feedback without ego.
## Workflow Read ticket from /factory/specs/TICKET-NNN.md — understand every acceptance criterion before writing a line Implement using TDD: write failing tests first, then make them pass Run the full local check suite (lint, format, typecheck, tests) — all green before committing Commit with a conventional commit message referencing the ticket ID Open a PR with: summary, linked ticket, test evidence, any known gaps Update /factory/status.json stage to "qa" and set prUrl Notify QA via sessions_send with ticket ID and PR URL
## Standards Never merge your own PRs — that is QA's gate Never push to main directly If a check suite fails, fix it before notifying QA — do not push a broken branch When QA returns a bug report, read it fully, reproduce the failure, fix root cause (not symptom)
## Tools Available exec — full shell access for build, test, git operations read / write / edit — source file manipulation sessions_send — notify QA or escalate to main web_search — look up docs, APIs, error messages
Design Notes
✅

Full exec — scoped by design

Dev has full shell access within its workspace. It can build, test, and commit. It cannot access other agents' workspaces. The /factory/ shared directory is the only cross-boundary surface.

🧪

TDD as a factory discipline

TDD is not optional in the factory model — it's the mechanism that makes acceptance criteria machine-verifiable. The QA agent validates the same tests Dev wrote. Disagreement on a failing test is a contract dispute, not a bug.

🔁

Handling QA feedback

When QA sends a bug report, Dev does not push a patch and re-open. Dev reads the report, reproduces the failure, identifies root cause, fixes it, re-runs the full suite, and only then notifies QA for a second pass.

📣

Escalation path

If Dev encounters an ambiguity the PM spec didn't resolve, or a technical blocker outside its scope, it escalates to main (Sir) via sessions_send rather than making an undocumented assumption.

Agent Persona

QA Engineer — SOUL.md

~/.openclaw/workspace-qa/SOUL.md
# SOUL.md — QA Engineer Agent > *"Trust nothing. Verify everything."* ## Identity You are a senior QA engineer in a software factory pipeline. You are sceptical by nature. Your job is to find what Dev missed — not to rubber-stamp their work.
## Workflow Read the PR diff and cross-reference against /factory/specs/TICKET-NNN.md Verify every acceptance criterion in Given/When/Then format — pass or fail, one by one Run the full test suite (unit, integration, E2E) and record the result Check coverage report — flag any acceptance criterion not covered by a test Write a structured verdict to /factory/reviews/pr-NNN-review.md Update /factory/status.json — set qaVerdict to "pass" or "fail" On pass: notify main with a summary and PR URL for approval On fail: notify dev with the review file path and a one-line summary of the blocking issue
## Review Format — pr-NNN-review.md Verdict: PASS / FAIL Criteria: table — criterion / status / evidence Test Results: suite name / count / pass / fail / skip Bugs: numbered list — title / steps to reproduce / expected / actual Coverage Gaps: acceptance criteria not covered by any test
## Constraints No write or edit on source files — you are read-only on the codebase Never approve a PR with a failing criterion — a partial pass is a fail Bug reports must include reproduction steps — not just "it doesn't work"
Design Notes
🔒

Read-only on source — enforced

QA's openclaw.json policy explicitly denies write and edit. It can run tests (exec) and read code, but cannot modify it. This separation of concerns prevents a QA agent from silently patching its way to a green suite.

📋

Structured verdict as the contract

The pr-NNN-review.md format is not a prose opinion — it's a structured record. Every criterion has an explicit pass/fail with evidence. This makes the verdict auditable and actionable without requiring conversational context.

🔁

The feedback loop

On fail, QA notifies Dev — not Sir. Sir is only pulled in when QA passes (for PR approval) or when the loop iterates more than a configured threshold, triggering an escalation. The factory handles its own rework within bounds.

🎯

Scepticism is the default

The QA SOUL.md explicitly frames the role as adversarial to Dev's output. This mirrors the human dynamic: effective QA engineers do not trust that the code works until they have independently verified it against the spec.

📁 Shared Filesystem

All agents read/write to /factory/ — specs, tickets, reviews, status. Artefacts persist between turns; no context is lost to compaction.

⚡ sessions_spawn

Dev can spawn parallel sub-agents for independent modules. Each sub-task runs concurrently and reports back on completion via sessions_send.

🛑 Human gates

The pipeline pauses naturally before any irreversible action — PR merge, production deploy, database migration — and waits for Sir's explicit approval.

Limitations & Roadmap

What works today — what comes next

Current Limitations
⚠

No native pipeline primitive

The PM → Dev → QA chain is orchestrated via sessions_send and SOUL.md standing instructions — not a built-in OpenClaw construct. Requires careful persona design to prevent instruction drift over long sessions.

⚠

Sub-agents cannot spawn sub-agents

OpenClaw currently prevents sub-agents from spawning their own sub-agents. Dev cannot farm out parallel modules unless orchestrated from the main session.

⚠

Context window budget

Each agent has a finite context window. Long-running tickets require careful file-based handoffs to prevent early decisions being lost to compaction. The /factory/ filesystem is the mitigation.

Recommended Next Steps
1

Bootstrap the three workspaces

Create workspace-pm, workspace-dev, workspace-qa with the SOUL.md files from slides 10–12 and the shared /factory/ directory structure.

2

Wire openclaw.json

Add agents, tool policies, and the agentToAgent allowlist. Restart the gateway and verify with openclaw agents list --bindings.

3

Pilot on a small ticket

Run a well-scoped feature through the full PM → Dev → QA pipeline. Observe where handoffs break down and iterate on the SOUL.md instructions accordingly.

4

Add a /factory command

A single trigger — "build feature X" — that kicks off the entire pipeline from main and delivers a Telegram summary when QA passes and Sir's approval is needed.

Summary

The Complete Picture

📚

Concept

6 decades, two convergent streams (SE + manufacturing), four core principles. The factory metaphor is established; the engineering discipline around it is still forming.

🤖

AI Inflection

Gen AI and agentic AI are the 2024–25 step-change. Not incrementally better tools — a qualitative shift in which roles can be automated and at what abstraction level the human operates.

🏗️

Architecture

PM, Dev, QA — three isolated agents, each with a SOUL.md persona and least-privilege tool policy. Shared /factory/ filesystem as the contract. sessions_send as the conveyor belt.

🧑‍✈️

Control

Sir stays in the loop at every irreversible gate. The factory is autonomous within stages — never unsupervised at the boundaries that matter: merge, deploy, escalation.
